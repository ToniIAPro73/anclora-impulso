# Isolated test database (integration tests)

Scope: exception `IMPULSO-TEST-DB-2026-10-12` in `.anclora/AOS_ADOPTION.md`. Synthetic data only.

| Item | Value |
|---|---|
| Compose project | `anclora-impulso-test` (`backend/docker-compose.test.yml`) |
| Container | `anclora-impulso-test-postgres` (image `postgres:16`) |
| Database | `anclora_impulso_test` (carries `anclora.test_marker = impulso-test-v1`) |
| Port | `127.0.0.1:54329` only (5432/5433 belong to other projects) |
| Volume | `anclora_impulso_test_pgdata` |
| Secrets | `backend/.env.test.local`, mode 600, git-ignored, generated by `init-env`; never printed |

## Commands (run from `backend/`)

```bash
./scripts/test-db.sh init-env   # create .env.test.local once (random local credentials)
./scripts/test-db.sh up         # start container and wait for healthcheck
./scripts/test-db.sh migrate    # prisma migrate deploy against the test DB only
./scripts/test-db.sh test [jest args]   # integration tests, clean env, guards active
./scripts/test-db.sh status
./scripts/test-db.sh down       # removes ONLY this project's container, network and volume
```

Optional extra cleanup of the local credentials file: `rm backend/.env.test.local`. No global Docker prune is needed or recommended.

## Guards
1. `scripts/test-db.sh` runs jest through `env -i`: operational `.env` values are not inherited, JWT secrets are local random values, LLM/SMTP credentials are absent.
2. `tests/support/integration-guard.ts` (isolated config): `DATABASE_URL` must be loopback with the expected port and name, and the live server must report the test marker; `dotenv` is mocked so `backend/.env` is not loaded.
3. `tests/support/default-integration-guard.ts` (default config): integration tests refuse to run unless started through the script or in CI with a loopback `DATABASE_URL`.

Prisma CLI prints "Environment variables loaded from .env" because it reads `backend/.env`; process variables take precedence and the printed datasource line (`127.0.0.1:54329`, `anclora_impulso_test`) is the effective target. Check that line.

## End-to-end (Playwright) against the same isolated database

```bash
# from the repository root (requires the container to be up: backend/scripts/test-db.sh up)
./scripts/e2e-isolated.sh            # API :3101 + Next dev :3100, runs e2e/, stops both; refuses if ports are busy
./scripts/e2e-isolated.sh e2e/session-and-fallback.spec.ts
./scripts/verify-runner-isolation.sh # observation-based proof that no operational env file contributes configuration
```
- Verifies loopback URL, port, name and the live `anclora.test_marker` before starting anything.
- Target end state is on: `IDEMPOTENCY_KEY_ENFORCEMENT=require`, `AUTH_ACCEPT_LEGACY_TOKENS=false`,
  `SECURITY_CONFIG_MODE=enforce`; access tokens last 5 s (`E2E_JWT_EXPIRES_IN`) so silent refresh is exercised.
- **Next runs from a copy of the sources that contains no `.env*` file** (`scripts/support/make-run-dir.sh`).
- **The API runs from an empty directory with a shielded environment** (`scripts/support/shield-env.sh`).
- Logs and screenshots go to `artifacts/qa/` (git-ignored). Synthetic exercises are named `E2E …`.

### Correction of earlier statements (2026-10-12)
Earlier versions of this document and of the delivery reports said the E2E stack never loaded operational
configuration. That was **wrong**, found by `scripts/support/env-probe.cjs`:
1. **API process:** Prisma's client loader reads `backend/.env` and merges its keys into `process.env` for keys that
   are *undefined*. `env -i` and an empty working directory do not prevent it. Before the shield, names such as
   `GROQ_API_KEY`, `GOOGLE_/GITHUB_OAUTH_*`, `ADMIN_EMAILS` were present in the API process
   (`artifacts/qa/env-probe-before-shield.log`, names only). The workout/coach code reads Groq only through
   `env.groqApiKey`, captured when `config/env.ts` loads — and every generated routine in those runs recorded
   `ai_unavailable`, so no provider call was made; OAuth endpoints read variables lazily but were never requested.
2. **Next process:** `__NEXT_PROCESSED_ENV` does **not** stop `next dev` from loading `.env.local`. Earlier E2E runs
   started Next from the repository root, so its process received the operational `.env.local` variables (names
   observed include database/Vercel variables and the login-autofill variables `UTILIZAR_USER_TEXT`/`USER_TEXT`/
   `PASS_TEXT`). The frontend code reads only `NEXT_PUBLIC_*`, `NODE_ENV` and the autofill variables, so no database
   access by the frontend is possible; the login form could have been pre-filled with the operator's stored
   credentials in those runs, and screenshots/traces under `test-results/` and `artifacts/qa/` from before this fix
   may show it. **Please review and delete `test-results/` (this agent's removal was blocked by a safety check).**
3. Servers from the first run were left running (process groups were not real groups) and later E2E runs silently
   talked to them. Fixed: `set -m`, refuse-if-port-busy, post-run listening check.
Current state (verified by `verify-runner-isolation.sh`): Next never stats or reads any repository-root `.env*`; the API
still *reads* `backend/.env` through Prisma's loader but nothing is applied because every name the backend reads is
predefined empty. A positive control proves the probe detects leakage when isolation is absent.

## Addendum 2026-10-12 — current isolation mechanism and run identity (supersedes the shield-only description)

**Real mechanism.** The API and jest no longer run from the working `backend/` tree. `scripts/support/clone-backend.sh`
builds, per run, an env-free clone (sources, prisma, tests, configs; `node_modules` via APFS clone, ~2 s). Prisma's
client resolves its env file relative to the generated client's real path, which is inside the clone, so the
operational `backend/.env` is **not in the loader's lookup path**. Next runs from `scripts/support/make-run-dir.sh`
(fresh copy, no `.env*`, no `.next`). The clone/copy are checked file by file against the working tree.
`scripts/verify-runner-isolation.sh` proves it by observation with controls: C1 (decoys applied when isolation is
absent), C2 (a **new** name in `.env` is applied even with the shield on — predefining known names is *not*
isolation), R1/R2 (nothing applied; no operational path stat'ed or read; R2 with the shield OFF).
The shield (`shield-env.sh`) remains as defence in depth only.

**Run identity.** Every run writes `identity.json`: run id, code identity (`git` head, `diffSha256`,
`sourceTreeSha256`), sanitized effective targets (database host/port/name, marker, container id, postmaster start;
AI/OAuth/SMTP predefined empty), configuration, and processes (script pid, roots, listeners, children).
E2E additionally proves that the listener on each port is **in the process tree this run started**, runs from this
run's copy (cwd), and answers a unique `/__run-<id>` request that appears in **this run's** log; it removes only its
own recorded processes and reports force-kills/survivors. A free port is a precondition, not a proof.
Artifacts: `artifacts/qa/runs/<id>/` (E2E), `backend/artifacts/test-runs/<id>/` (integration).
